# «Пташеня» — власний хостинг на Windows

React/Vite + Express + PostgreSQL. Production-запуск обслуговує зібраний сайт і `/api` **одним Node.js-процесом на http://127.0.0.1:8080**. Vite dev server, Replit-проксі, Replit CLI, Nix і Docker для цього не потрібні.

## 1. Встановити на ПК

- **Node.js 24 LTS (64-bit)**: https://nodejs.org/
- **PostgreSQL 16 або новіший**, разом із pgAdmin: https://www.postgresql.org/download/windows/
- Git і VS Code — для завантаження/редагування коду.
- pnpm — цей monorepo використовує `workspace:` і `catalog:`, тому **npm install не підтримується**. npm потрібен тільки для встановлення pnpm:

```powershell
npm install --global pnpm@10.26.1
```

Після встановлення перезапустіть термінал. Склонуйте приватний GitHub-репозиторій або розпакуйте весь проєкт. Усі подальші команди виконуйте в **корені проєкту**, де є цей README та `pnpm-workspace.yaml`.

```powershell
pnpm install --frozen-lockfile
Copy-Item .env.example .env
```

Не копіюйте `node_modules` або готову Linux-збірку з Replit: залежності мають встановлюватися заново на Windows. Залежності для Windows більше не виключені з lockfile.

## 2. Заповнити `.env`

Відкрийте `.env` у VS Code. Реальні значення не надсилайте в чат і не публікуйте в GitHub.

| Змінна | Призначення |
| --- | --- |
| `DATABASE_URL` | Обов’язкове підключення до вашої PostgreSQL, приклад у шаблоні. Спецсимволи пароля в URL треба URL-кодувати. |
| `VITE_CLERK_PUBLISHABLE_KEY` | Обов’язковий **публічний** ключ Clerk, вбудовується у frontend під час збірки. |
| `CLERK_PUBLISHABLE_KEY` | Той самий публічний ключ для сервера. |
| `CLERK_SECRET_KEY` | Секретний ключ тієї самої Clerk-інстанції, тільки на сервері. |
| `ADMIN_EMAIL` | Обов’язкова адреса власника, якою він входить у Clerk. Не пароль. |
| `PORT` | Порт production-сервера, за замовчуванням **8080**. |
| `HOST` | За замовчуванням **127.0.0.1**, тільки цей ПК/локальний тунель. Для LAN можна свідомо вибрати `0.0.0.0` і налаштувати firewall. |
| `NODE_ENV` | `production`; production-команди встановлюють це автоматично. |
| `LOG_LEVEL` | `info` за замовчуванням; також `debug`, `warn`, `error`. |
| `VITE_CLERK_PROXY_URL` | Необов’язковий URL проксі, **тільки якщо він налаштований для вашої Clerk-інстанції**. Інакше залиште порожнім. |
| `TOYSI_PHONE`, `TOYSI_PASSWORD` | Необов’язкова пара для входу до постачальника. |
| `DISABLE_SUPPLIER_SYNC` | `true` під час перенесення. `false` вмикає планувальник синхронізації, якщо це також дозволено налаштуваннями магазину. |
| `MOIE_URL`, `MOIE_WEBHOOK_TOKEN` | Необов’язкова пара для CRM. Порожні значення вимикають інтеграцію. |
| `API_PORT`, `VITE_PORT` | Тільки режим розробки: 8080 і 5173. |
| `BASE_PATH` | `/` для самостійного хостингу. Production-збірка фіксує `/`. |

`LOCAL_DEV`, `VITE_STANDALONE`, `SERVE_STOREFRONT`, `STOREFRONT_DIR` виставляються скриптами автоматично. `BASE_URL`, `DEV`, `PROD`, `MODE` — внутрішні значення Vite, їх не треба заповнювати. `REPL_ID` використовується лише для необов’язкових інструментів розробки всередині Replit. Жодні `REPLIT_*`, `PGHOST` тощо не потрібні, коли заданий `DATABASE_URL`. `SESSION_SECRET` поточний код не використовує.

Успадковані змінні Windows мають пріоритет над `.env`: якщо зміна `.env` не діє, перевірте системні змінні. Не зберігайте `.env` у загальнодоступній папці.

### Важливо про авторизацію

Авторизація залишається **Clerk**, а не локальною системою паролів. Власний сервер усе одно потребує інтернету до Clerk, постачальника й CRM.

Поточна інстанція Clerk керується Replit. Перенесення коду **не передає керування цією інстанцією** та не переносить облікові записи автоматично. Для незалежності від Replit потрібна власна Clerk-інстанція зі своїми ключами та налаштуваннями production-домену. Код приймає стандартні Clerk-ключі через `.env`; постачальника авторизації та наявні акаунти тут не змінено. Не видаляйте чинну інстанцію: спочатку окремо сплануйте збереження/перенесення користувачів та зв’язків із замовленнями.

Не змішуйте test/live ключі або ключі різних інстанцій. Для публічного магазину використовуйте production-конфігурацію Clerk. Змінили будь-яку `VITE_*` змінну — **повторіть `pnpm build`**, одного перезапуску недостатньо.

Автономна збірка використовує саме вказаний ключ, а не генерує його з hostname, як Replit-managed збірка. Це дозволяє підключити власну Clerk-інстанцію без залежності від Replit DNS. Production-вхід на власному домені все одно потрібно перевірити з реальною конфігурацією вашої інстанції.

## 3. Підготувати PostgreSQL

У pgAdmin створіть окрему роль із паролем та базу `ptashenya`, власником якої буде ця роль. Запишіть локальні дані підключення у `DATABASE_URL`. Служба PostgreSQL має автоматично стартувати з Windows.

**Якщо база нова та порожня:**

```powershell
pnpm run local:db:init
```

Це створює таблиці, **але не переносить товари/замовлення**. Не використовуйте цю команду для робочої бази без резервної копії й перевірки змін схеми.

**Якщо переносите чинний магазин:** спочатку потрібні захищений експорт і відновлення бази у PostgreSQL на ПК. Код із GitHub не містить даних магазину, а акаунти Clerk не містяться у цій PostgreSQL. Не записуйте робочі дані у GitHub. Не підключайте локальну копію до чинної бази Replit: синхронізація й замовлення можуть змінити робочі дані.

## 4. Зібрати та запустити production

```powershell
pnpm build
pnpm start
```

`pnpm build` перевіряє TypeScript та збирає тільки API і магазин, а не Canvas/пісочницю. Потрібен заповнений публічний Clerk-ключ; секрети у frontend не потрапляють. Збірка не запускає синхронізацію, не підключається до бази й не змінює її схему.

Після заповнення `.env` можна перевірити ізольований production-запуск (без синхронізації та CRM):

```powershell
pnpm run test:production
# Додатково перевірити читання категорій із вашої бази:
pnpm run test:production -- --database
```

`pnpm start` читає `.env`, перевіряє наявність збірки та обов’язкових налаштувань і запускає **один production-процес**:

- сайт: http://127.0.0.1:8080
- перевірка API: http://127.0.0.1:8080/api/healthz
- вхід і кабінет власника — через звичайні сторінки магазину;
- вкладені посилання, наприклад `/catalog`, працюють після оновлення сторінки.

`/api/healthz` підтверджує лише роботу процесу, не справність бази чи CRM. Окремо перевірте завантаження каталогу, авторизацію власника й потрібні інтеграції.

Зупинити вручну: `Ctrl+C`. Змінити порт — змініть `PORT` у `.env` і перезапустіть. `API_PORT` не змінює production-порт.

Прямий еквівалент, наприклад для Планувальника завдань:

```powershell
node scripts/start-production.mjs
```

Не запускайте production через `local:dev` або `vite preview`. Після оновлення коду: зупиніть сервер, зробіть резервну копію, виконайте `pnpm install --frozen-lockfile`, `pnpm build`, потім `pnpm start`. Зміни схеми бази застосовуйте окремо після перевірки, не автоматично при старті.

## 5. Автозапуск 24/7 на Windows

Вбудований **Планувальник завдань Windows** не потребує PM2 чи додаткового менеджера процесів.

1. Покладіть проєкт у постійну папку, наприклад `C:\Ptashenya`. Уже налаштуйте `.env`, базу і виконайте збірку.
2. Відкрийте «Планувальник завдань» → «Створити завдання».
3. Виберіть окремого Windows-користувача, який має доступ до проєкту й `.env`. Дозвольте запуск незалежно від входу користувача. Адміністративні права застосунку не потрібні.
4. Тригер: «Під час запуску системи», із затримкою 60 секунд для PostgreSQL/мережі.
5. Дія → програма: `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`.
6. Аргументи (замініть шлях своїм):

   ```text
   -NoProfile -ExecutionPolicy Bypass -File "C:\Ptashenya\scripts\start-windows.ps1"
   ```

7. Робоча папка: `C:\Ptashenya`.
8. Налаштування: перезапуск після помилки через 1 хвилину; забороніть одночасні копії; вимкніть обмеження тривалості на 3 дні. Не зупиняйте завдання через простій чи перехід на батарею.
9. Служба PostgreSQL має бути в режимі автоматичного запуску. `node.exe` має бути доступний у PATH обраного користувача.
10. Вручну запустіть завдання, перевірте сайт, потім перевірте його після перезавантаження ПК.

Журнали обгортки зберігаються у `logs/store-YYYY-MM-DD.log` (дата запуску; новий файл при наступному запуску). Видаляйте/архівуйте старі журнали за своїм графіком; туди можуть потрапляти технічні деталі, тому не публікуйте їх.

Для ручної роботи не запускайте другу копію паралельно із завданням: буде помилка зайнятого порту. Для зупинки завдання завершіть також його Node-процес через Диспетчер завдань і перевірте звільнення порту.

ПК не повинен засинати чи вимикатися; потрібні стабільний інтернет, оновлення безпеки та бажано ДБЖ. Після зникнення світла/інтернету домашній сайт буде недоступним.

## 6. Доступ покупцям через домен

Локальний запуск сам собою **не відкриває сайт в інтернет**. Рекомендована схема:

```text
Покупець → HTTPS / ваш домен → Cloudflare Tunnel → http://127.0.0.1:8080
                                                    ├─ сайт
                                                    └─ /api → локальна PostgreSQL
```

Для цього потрібен окремий агент **cloudflared** як Windows-служба. Cloudflare One Client / WARP у режимі DNS не замінює Tunnel. Налаштування DNS/HTTPS і самого тунелю виконуються окремо; цей код не змінює домен і не відкриває порти.

Не відкривайте порт PostgreSQL (5432) в інтернет. Залиште `HOST=127.0.0.1` за локальним тунелем. За поточної конфігурації довіряються лише локальні проксі. Якщо використовуєте інший зворотний проксі, його довіру треба налаштувати окремо.

Домен лишається у NIC.UA. Під час переходу на Cloudflare DNS збережіть MX/TXT та записи підтвердження Google. Не вимикайте чинний сайт і не змінюйте DNS, доки локальна production-копія, дані, авторизація і замовлення не перевірені.

## Резервні копії та безпека

- Код — у приватному GitHub; `.env`, база, експорти й `logs/` виключені з Git.
- Щодня робіть резервну копію PostgreSQL через pgAdmin/pg_dump на **інший носій**, перевіряйте відновлення. Зберігайте копію `.env` окремо, із захищеним доступом.
- Замовлення містять персональні дані: не публікуйте резервні копії чи журнали.
- Коренем вебсервера є лише `artifacts/baby-shop/dist/public`, не весь репозиторій.
- Не застосовуйте `npm audit fix --force` і не змінюйте lockfile навмання.

## Режим розробки (не для покупців)

```powershell
pnpm run local:dev
```

Сайт: http://localhost:5173; API: 8080. Синхронізація постачальника в цьому режимі примусово вимкнена. Детальніше: [WINDOWS_SETUP.md](WINDOWS_SETUP.md).

## Типові помилки

- **Fill these variables…** — заповніть названі змінні у `.env`, не значення з шаблону.
- **Production files are missing** — виконайте `pnpm build` у корені.
- **Clerk public keys must match…** — ключі frontend/backend і збірки мають збігатися; перезберіть.
- **EADDRINUSE** — порт зайнятий; зупиніть попередню копію або змініть `PORT`.
- **ECONNREFUSED / password authentication failed** — перевірте службу PostgreSQL та `DATABASE_URL`.
- **На сайті немає товарів** — GitHub не переносить базу, потрібне відновлення каталогу.
- **Native module / esbuild / rollup missing** — не копіюйте Linux `node_modules`; встановіть залежності на Windows із поточним lockfile.
